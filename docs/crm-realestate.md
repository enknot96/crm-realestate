## 0. このプロジェクトの目的

**第一目的は開発者（以下「私」）の TypeScript / フルスタックのスキルアップである。**
動くものを最速で作ることではない。ポートフォリオとして通用する品質の成果物を、
自分で設計判断を下しながら組み上げることが目的。

副次的な目的として、実在する業務要件（不動産1人事業者の顧客管理・LINE 追客）を
満たすデモを作り、営業資料として使える状態にする。

### 想定ユーザー（架空の設定として実装する）

不動産業（空き家管理・売買仲介）を1人で営む事業者。IT の専門知識なし。
スマートフォンが主な業務端末。以下の3つを自動化したい。

1. LINE 登録者に「売主」「買主」等のタグを付け、属性別に配信する
2. 契約日を基準に「2週間ごとの業務報告期限」「3ヶ月ごとの更新時期」を自分に通知する
3. 現場写真をアップすると報告書が生成され、確認・修正のうえ顧客の LINE に送信される

### 絶対に外せない制約

- **ランニングコストを抑える。**開発・デモは各サービスの無料枠内で完結させる
- **IT 初心者が単独で運用できる。**専門用語が画面に出てこない
- **誤送信を構造的に防ぐ。**売主向けの内容が買主に届く事故は事業を終わらせる

### コストについての立ち位置

デモは無料枠で構築する。ただし「月額完全0円」を約束はしない。
商用稼働時には、ホスティング（Vercel は Hobby プランが非商用限定のため Pro が必要）と
LINE の通数超過分で費用が発生しうる。聞かれたら正直に答える、という温度感で扱う。
設計を縛る制約としては扱わない。

## 1. ペアプロ規約（Claude Code はここを厳守する）

この規約はプロジェクトの成否を分ける。**実装を急いで飛ばさないこと。**

### 1-1. 実装の順序

各タスクは必ずこの順で進める。

```
① Claude が「設計の選択肢」を2〜3案、トレードオフ付きで提示する
② 私が選ぶ。私が選ばずに「お任せ」と言った場合のみ Claude が決める
③ 私が実装を書く。Claude はコードを先回りして書かない
④ 詰まったら私が明示的に「書いて」「ヒントちょうだい」と言う
⑤ Claude がレビューする。動くかどうかではなく、型設計・命名・責務分離を見る
```

### 1-2. Claude が勝手にやってはいけないこと

- **聞かれていないファイルを作らない。**「ついでに〜も作っておきました」は禁止
- **`any` / `as` / `@ts-ignore` で型エラーを黙らせない。**型が通らないのは設計が間違っているサイン。設計に戻る
- **エラーハンドリングを `try { } catch { }` の握りつぶしで済ませない**
- **私が書いたコードを勝手に書き直さない。**問題点を指摘して、直すかどうかは私が決める
- **フェーズを飛ばさない。**「Phase 4 も一緒にやりますか？」と提案しない

### 1-3. Claude が積極的にやること

- 私が書いたコードに対して「この型はもっと狭くできる」「この関数は2つの責務を持っている」と指摘する
- 私が安易な選択をしたとき（`string` で済ませた、バリデーションを省いた等）は必ず指摘する。
  そのうえで「今はこれでよい」という判断も許容する
- 各フェーズの終わりに「このフェーズで何を学んだか」を1分で振り返らせる
- 詰まったときはコードではなく **考え方** を先に出す

### 1-4. 私が言いがちな NG ワードと、そのときの対応

| 私が言うこと | Claude の対応 |
|---|---|
| 「全部書いて」 | 一度だけ「学習目的から外れますが本当に？」と確認。2回目は素直に書く |
| 「とりあえず動けばいい」 | 動く最小実装を出したうえで、後で返済すべき技術的負債を TODO コメントで残す |
| 「型がわからん」 | 完成形を出さず、型パズルを段階的に分解して一緒に解く |

## 2. 技術スタック

| 領域 | 採用 | 選定理由 |
|---|---|---|
| 言語 | TypeScript (strict) | 本プロジェクトの主目的 |
| フレームワーク | Next.js App Router | Webhook・管理画面・LIFF・画像生成を1リポジトリに収容できる |
| ホスティング | Vercel (Hobby) | デモ用途。※商用は Pro が必要（セクション2-2） |
| DB | Neon (Postgres) | 無料枠。ブランチ機能が開発に便利 |
| ORM | Drizzle ORM | スキーマから型が生える。SQL に近くて学習になる |
| バリデーション | Zod | 環境変数・フォーム・LLM 出力の単一の真実源 |
| LINE | `@line/bot-sdk` | 署名検証と型定義が揃っている |
| ストレージ | **Cloudflare R2** | 写真と生成画像。エグレス無料。Blob は使わず R2 に一本化 |
| 画像配信 | **Cloudflare Workers** | 署名付き短期URLで報告書画像を配信（Phase 4） |
| 画像生成 | `next/og` (ImageResponse) | 報告書を PNG で生成。JSX がそのまま画像になる |
| AI | Vercel AI SDK v6 + `@ai-sdk/google` (Gemini) | 画像入力の無料枠が実用的。`generateText` + `Output.object()` |
| 定期実行 | GitHub Actions (cron) | Vercel Hobby の cron は頻度制限があるため |
| テスト | Vitest + Playwright（スモーク1本のみ） | ドメインのユニットテスト中心。E2E は網羅しない |
| 認証 | 自前セッション (`jose` で JWT 署名) | 単一ユーザーなので Auth.js は過剰。Cookie とセッションの仕組みを理解する |

### 2-1. 無料枠の内訳（開発・デモ時）

| サービス | 無料枠 | 注意点 |
|---|---|---|
| Vercel Hobby | 100GB 転送 / 1M 関数実行 | **非商用限定。**デモ・ポートフォリオ用途のみ |
| Neon | 0.5GB / コンピュート時間制限あり | アイドルでサスペンド（INV-5 で対策） |
| Cloudflare Workers | 10万リクエスト/日 | 商用利用の制限なし |
| Cloudflare R2 | 10GB / エグレス無料 | **有効化にクレジットカード登録が必要** |
| Google AI Studio (Gemini) | 無料枠あり・画像入力対応 | 無料枠のデータは品質改善に利用されうる → INV-2 で手当済み |
| LINE 公式アカウント | 200通/月 | 開発用に本番とは別のアカウントを作る |
| GitHub Actions | 2,000分/月 | cron 用途では誤差 |

R2 のカード登録に抵抗がある場合は、Vercel Blob にフォールバックしてよい。
その場合 Phase 4 の Workers 部分は独立した学習タスクとして切り出す。

### 2-2. Vercel Hobby の非商用制限について

Vercel の Fair Use Guidelines では、Hobby プランは非商用の個人利用に限定され、
商用利用には Pro（$20/月）以上が必要とされている。
商用の定義は広く、「制作に関わった者（コードを書いた有償のコンサルタントを含む）の
金銭的利益のためのデプロイ」が該当する。

本プロジェクトは学習・ポートフォリオ目的なので Hobby で問題ない。
ただし実案件として納品する場合は Pro が必要になる。顧客に聞かれたら正直に伝える。

なお、Hobby プランのコンテンツはモデル学習に利用される可能性がある（チーム設定でオプトアウト可）。
デモは架空データなので実害はないが、把握しておくこと。

### 2-3. 使わないもの（意図的な不採用）

- **GAS**：学習価値が低い。ただし「なぜ GAS でないのか」は説明できるようにする
- **narrowcast API / オーディエンス API**：デモグラフィック配信は対象50人未満だと送信できず、
  小規模事業者では実用にならない。**multicast（最大500 ID/回）で十分**
- **Cloudflare Queues**：有料プラン。非同期処理は DB のジョブテーブル + cron で代替する
- **Vercel Blob**：R2 に一本化する
- **状態管理ライブラリ**：Server Components + Server Actions で足りる範囲に留める

## 3. 学習テーマ

各フェーズに紐づく形で配置してある。ここを意識せずに実装すると、ただの CRUD になる。

### 型設計

- **Branded Types**：`CustomerId` と `LineUserId` を型レベルで区別する。
  学習のためだけでなく、**取り違え事故を型で防ぐ**という実務要件そのもの
- **判別可能なユニオン**：LINE の Webhook イベント、報告書のステート
- **網羅性チェック**：`never` を使った `assertNever` でユニオンの取りこぼしをコンパイル時に検出
- **`satisfies`**：定数オブジェクトに型制約をかけつつリテラル型を維持する
- **Zod からの型導出**：`z.infer` を使い、スキーマとインターフェースを二重管理しない
- **opaque token パターン**：不変条件を型で強制する（INV-1）

### アーキテクチャ

- ドメインロジックを Next.js から独立させる（`src/domain` は React も Next も import しない）
- Repository パターンで DB アクセスを隔離し、ドメインのテストを DB なしで回す
- **依存性逆転**：`MessageSender` インターフェースを定義し、
  `LineMessageSender` / `FakeMessageSender` を差し替える。
  `if (DEMO_MODE)` をドメインに散らかさないための実践
- **Result 型**：外部 API 呼び出しは失敗が日常。例外ではなく戻り値で失敗を表現する
- **冪等性を多層で守る**：アプリ層の制御に加え、**DB の部分一意インデックスで裏打ちする**。
  アプリの論理を DB 制約で保証するという発想を身につける

### 実務的な勘所

- Webhook を即座に 200 で返し、重い処理を後段に逃がす
- タイムゾーン（JST）の扱い。日付境界のバグは必ず踏む
- 秘密情報の扱い。LLM に PII を渡さない設計上の分離
- 外部から取得される URL の保護（署名付き短期 URL）
- エッジランタイムの制約（ネイティブモジュールが使えない）

## 4. ドメインモデル

### 4-1. 中核の概念

```
Customer（顧客）
  ├─ 0..1 LineFriend（LINE 友だち）  ※紐付いていない顧客も、紐付いていない友だちも存在する
  ├─ 0..n Tag（売主 / 買主 / 管理オーナー ...）
  ├─ 0..n Property（管理物件）
  └─ lastContactedAt（最終接触日）

Property（物件）
  └─ 0..n PatrolReport（巡回報告）
        state: draft → reviewing → approved → sent
                                  └→ failed

Contract（契約）
  └─ 0..n ReminderRule（2週間ごと / 3ヶ月ごと）
        └─ 0..n ReminderOccurrence（発火予定・発火済み）

Broadcast（配信）
  ├─ segment: TagFilter
  └─ scheduledAt: Date | null   ※ null なら即時配信

MessageLog（送信ログ）  ※通数カウントの根拠
```

**重要な設計判断**：`Customer` と `LineFriend` は別テーブルにする。
LINE で友だち追加した人が誰なのかは最初わからないし、
LINE を使っていない顧客も存在する。1テーブルに押し込むと必ず破綻する。

### 4-2. Branded Types の定義

```ts
// src/domain/shared/branded.ts
declare const brand: unique symbol;
type Brand<T, B> = T & { readonly [brand]: B };

export type CustomerId  = Brand<string, 'CustomerId'>;
export type LineUserId  = Brand<string, 'LineUserId'>;
export type PropertyId  = Brand<string, 'PropertyId'>;
export type ReportId    = Brand<string, 'ReportId'>;
```

これにより `sendTo(lineUserId)` に `CustomerId` を渡すとコンパイルエラーになる。
**このプロジェクトで一番事故りやすい箇所を、型で塞いでいる。**

### 4-3. 報告書のステートマシン

```ts
type ReportState =
  | { kind: 'draft';     photos: PhotoRef[] }
  | { kind: 'reviewing'; photos: PhotoRef[]; body: string; generatedBy: 'ai' | 'human' }
  | { kind: 'approved';  photos: PhotoRef[]; body: string; approvedAt: Date }
  | { kind: 'sent';      photos: PhotoRef[]; body: string; sentAt: Date; messageId: string }
  | { kind: 'failed';    photos: PhotoRef[]; body: string; error: string };
```

`approved` を経由せずに `sent` へ遷移できないことを、型と遷移関数で保証する。
これが顧客の言う「確認・修正してから送信ボタン」の実装形。

## 5. 不変条件（コードで守るべきルール）

Claude Code はこれらに違反する実装を提案しない。レビュー時も必ずチェックする。

### INV-1. 送信は必ず QuotaGuard を通る

LINE の無料プランは月200通。「送った人数 × 回数」でカウントされる。
プッシュ送信を行う関数は `QuotaGuard` が発行したトークンを引数に要求する。
Guard を経由しない直接送信はコンパイルエラーになる設計にする。

```ts
// 概念。実装は Phase 3 で自分で設計する
declare const guarded: unique symbol;
export type SendPermit = { readonly [guarded]: true; count: number };
// permit は QuotaGuard.reserve() でしか生成できない
export function pushMessages(permit: SendPermit, ...): Promise<Result<...>>;
```

コスト対策であると同時に、**誤送信を防ぐ確認 UI の土台**でもある。

### INV-2. LLM に PII を渡さない

プロンプトに渡してよいもの：写真、物件の構造的属性（木造/2階建て等）、観察項目のチェック結果。
渡してはいけないもの：顧客氏名、住所、電話番号、物件の所在地、契約金額。

`buildPatrolPrompt()` の入力型を PII を含まない型に限定し、
`Customer` 型をそのまま受け取れないようにする。

### INV-3. アップロード画像の EXIF は必ず除去する

空き家＝不在が確定した物件の位置情報が写真に埋まる。
アップロード直後、保存前にサーバー側で除去する。クライアント任せにしない。

### INV-4. 配信前に宛先の実数と内訳を表示する

「売主タグ 12名に送信します（今月の残り 63通）」を確認モーダルで必ず出す。
タグ名を手入力させる確認を入れる。**この摩擦は意図的に残す。**

### INV-5. Webhook は 3 秒以内に 200 を返す

署名検証 → イベントを永続化 → 即 200。処理は後段。
Neon の無料プランはアイドルでサスペンドするため、この設計は必須。

### INV-6. 外部 API 呼び出しは Result 型で返す

LINE API、Gemini、R2 へのアクセスは throw しない。
`Result<T, E>` を返し、呼び出し側に処理を強制する。

### INV-7. 外部公開する画像 URL は署名付き・短期有効にする

LINE の image message は LINE 側サーバーが URL を取得するため、認証をかけられない。
素朴に実装すると、物件写真と報告内容が誰でも見られる公開 URL になる。

有効期限付き署名トークンを URL に含め、Workers 側で検証する。
LINE は取得した画像を自前でキャッシュするため、有効期限は数分で足りる。

### INV-8. 画面に専門用語を出さない

「通数」「クォータ」「セグメント」「配信ジョブ」「タスクキュー」は画面に出さない。
不動産業の人が読んで意味がわかる日本語にする。
例：「今月あと63件送れます」「送る相手：売主のお客様 12名」

## 7. 実装フェーズ

各フェーズは「動く状態」で終わること。中途半端な状態で次に進まない。

---

### Phase 0 — 基盤と型の土台

**目的**：後から効いてくる土台を先に作る。ここを雑にすると全部に響く。

**やること**

- Next.js プロジェクト初期化、`tsconfig` を strict + `noUncheckedIndexedAccess` に
- `src/config/env.ts`：Zod で環境変数を検証。起動時に落ちるようにする
- `src/domain/shared/` に Branded Types、`Result` 型、`assertNever` を実装
- ESLint で `src/domain` から React/Next への import を禁止
- Vitest セットアップ、`Result` 型のテストを1本書いて回ることを確認
- Neon にプロジェクト作成、Drizzle 接続確認

**学習テーマ**：`unique symbol` による branding、`z.infer`、判別可能ユニオンとしての Result

**完了条件**
- `pnpm typecheck` `pnpm lint` `pnpm test` が全て通る
- 環境変数を1つ消すと、起動時に「何が足りないか」が明示されて落ちる

**詰まりどころ**：`noUncheckedIndexedAccess` を入れると配列アクセスが全て `T | undefined` になる。
最初は面倒だが、これに慣れることが目的の一部。オフにしない。

---

### Phase 1 — LINE Webhook と友だち登録

**目的**：外部からのイベントを受け取り、永続化する。ここが動くと一気に実感が湧く。

**やること**

- `POST /api/line/webhook`
  - `@line/bot-sdk` の `validateSignature` で署名検証（**生のリクエストボディが必要**）
  - `webhookEventId` を保存して冪等性を確保（LINE は同じイベントを再送する）
  - イベント種別を判別可能ユニオンで分岐し、`assertNever` で網羅性を担保
  - `follow` / `unfollow` / `message` を処理。それ以外は記録だけして無視
- `line_friends` テーブルに `lineUserId`, `displayName`, `followedAt`, `blockedAt` を保存
- ローカル開発用のトンネル手順を README に書く（Cloudflare Tunnel か ngrok）

**学習テーマ**：Web 標準の Request/Response、生ボディの取得、HMAC 署名検証の仕組み、
判別可能ユニオンの網羅性チェック、冪等性

**完了条件**
- 自分のスマホで友だち追加すると DB に行が増える
- ブロックすると `blockedAt` が入る
- 同じイベントを curl で2回投げても行が重複しない
- **署名が不正なリクエストは 401 で弾かれる**（テストを書く）

**詰まりどころ**
- Next.js App Router で生ボディを取るには `await req.text()`。`req.json()` を先に呼ぶと署名検証が失敗する
- 検証は必ず開発用の LINE 公式アカウントで行う。稼働中のアカウントに Messaging API を
  後付けすると既存の自動応答設定が変わる

### Phase 3 — タグ配信・通数ガード・予約配信 ★提案の目玉

**目的**：誤送信を構造的に防ぐ仕組みを、型とUIの両方で実装する。

**やること**

- `QuotaGuard`：今月の送信数を集計し、上限（デフォルト200）との差分を管理
  - LINE の `GET /v2/bot/message/quota` と `/quota/consumption` から実測値も取得し、
    ローカルの集計とズレたら実測値を優先する
- **INV-1 の opaque token パターンを実装する。**
  `QuotaGuard.reserve(n)` が `SendPermit` を返し、`pushMessages` はそれを要求する
- **`MessageSender` インターフェースを定義**し、`LineMessageSender` を実装する。
  ドメインは具象を知らない（DEMO_MODE 対応の土台）
- タグでセグメントを解決し、`multicast`（最大500 ID/回、チャンク分割）で送信
- 送信前の確認モーダル：宛先タグ名・実人数・消費通数・残通数を表示。タグ名の手入力確認
- 画面上部に常設の通数メーター（表記は「今月あと63件送れます」）
- 送信結果を `message_logs` に記録。ブロック済みユーザーへの失敗を握りつぶさない
- **予約配信**：`scheduledAt` を持たせ、Phase 5 の cron から発火させる
  - ステップ配信は「予約配信の連鎖」なので、データモデルが対応可能であることを示せる

**学習テーマ**：opaque token による不変条件の型的強制、依存性逆転、配列のチャンク分割、
部分的失敗を含む一括処理の結果型設計、予約実行のスケジューリング

**完了条件**
- 上限を超える配信を実行しようとすると、送信前に止まる
- 「売主」タグを付けた自分のテストアカウントにだけメッセージが届く
- 送信ログから今月の消費通数が正確に出る
- **`QuotaGuard` を経由せずに `pushMessages` を呼ぶコードがコンパイルエラーになる**
- 予約した配信が指定時刻に送信される

**この Phase の意味**：通数が「人数 × 回数」でカウントされることを理解して設計に
落としている応募者はほとんどいない。デモの説得力の多くはここで決まる。

### Phase 4a — 巡回報告：アップロードから AI 草案まで

**目的**：外部ストレージと LLM を扱う。ここで一度必ず動く状態を作る。

**やること**

1. **写真アップロード**：スマホのカメラから複数枚。Cloudflare R2 へ
   - R2 は S3 互換なので `@aws-sdk/client-s3` で扱える
2. **EXIF 除去**（INV-3）：`sharp` でサーバー側処理してから保存。クライアント任せにしない
3. **AI による報告文の草案生成**
   ```ts
   import { generateText, Output } from 'ai';
   import { google } from '@ai-sdk/google';

   const { output } = await generateText({
     model: google('gemini-2.5-flash'),
     output: Output.object({ schema: patrolObservationSchema }),
     messages: [{ role: 'user', content: [{ type: 'image', image: url }, ...] }],
   });
   ```
   - **PII を渡さない**（INV-2）。プロンプト構築関数の入力型で強制する
   - **`Output.object()` はプロバイダの JSON モードを使わず、自由文をクライアント側でパースする。**
     モデルが JSON をコードフェンスで包むと失敗する。
     `extractJsonMiddleware` を `wrapLanguageModel` で噛ませるか、リトライを実装する
   - 失敗時は空の草案を返し、人が手入力できる状態に落とす（画面を壊さない）

**学習テーマ**：マルチパートアップロード、S3 互換 API、画像処理、
LLM の構造化出力とその失敗の扱い、ミドルウェアによる挙動の差し込み

**完了条件**
- スマホで撮影 → アップロード → AI 草案が画面に出る
- AI を意図的に失敗させても（不正なモデル名等）、画面が壊れず手入力に落ちる
- **アップロードした写真から EXIF が消えていることを実際に確認する**（`exiftool` で検証）

### Phase 4b — 巡回報告：承認から LINE 送信まで ★技術的な山場

**目的**：ステートマシン、署名付き URL、エッジでの配信をつなぐ。

**やること**

1. **承認フロー**：4-3 のステートマシンを実装。`approved` を経ずに `sent` にできない
2. **二重送信の防止を二層で**
   - アプリ層：ステート遷移関数で `sent` からの再遷移を禁止
   - DB 層：**部分一意インデックス**で `sent` 状態の行が1つしか作れないようにする
3. **報告書 PNG の事前生成**
   - **承認時に生成して R2 に保存する。**オンデマンド生成にしない
   - `ImageResponse` の生成が遅いと LINE 側の取得がタイムアウトして無言で失敗する
   - **日本語フォントを明示的に読み込まないと豆腐になる。**Noto Sans JP のサブセットを用意
   - `satori` は WOFF2 を扱えない。TTF / OTF / WOFF を使う
4. **Cloudflare Worker による署名付き配信**（INV-7）
   - `workers/image-delivery/`：`?exp=...&sig=...` を検証し、R2 から画像を返す
   - 署名は HMAC。Phase 1 の LINE 署名検証で学んだ仕組みがそのまま応用できる
   - 有効期限は5分程度。LINE は取得後に自前でキャッシュする
5. **LINE 送信**：image message（HTTPS 必須、original 最大10MB / preview 最大1MB）
   - Messaging API は PDF を送れない。PDF が必要なら別途リンクをテキストで添える

**学習テーマ**：ステートマシンの型的表現、DB 制約による並行性制御、
JSX からの画像生成、HMAC 署名付き URL、Workers と R2 のバインディング、
エッジランタイムの制約（`sharp` は動かない、を体で知る）

**完了条件**
- 承認 → 自分の LINE に報告書画像が届く
- 承認済みの報告書を2回送信しようとしても1回しか送られない（**DB 制約でも弾かれる**）
- 生成画像に日本語が正しく描画されている
- 署名なし・期限切れの URL でアクセスすると 403 が返る

### Phase 5 — リマインドと通知センター

**目的**：日付計算という、地味に一番バグる領域を正面から扱う。

**やること**

- `contracts` テーブルに契約日と種別を保存
- `ReminderRule`：「契約日から2週間ごと」「契約日から3ヶ月ごと」を表現する型を設計
- 次回発火日を計算する純粋関数を `src/domain/reminder` に。**ここは徹底的にテストを書く**
  - 月末（1/31 の3ヶ月後は？）、うるう年、JST と UTC の境界
- GitHub Actions の cron から `POST /api/cron/reminders` を叩く。秘密トークンで保護
  - 同じエンドポイントで Phase 3 の予約配信も発火させる
- **通知先は自分のメール（または Google Chat webhook）。LINE は使わない**

- **アプリ内「通知センター」画面**
  - 発火した通知の履歴を一覧表示する
  - メール送信だけだとデモを触った人に何も見えないため、可視化は必須

**学習テーマ**：日付演算の落とし穴、純粋関数とテスト、タイムゾーン、
cron ジョブの冪等性（同じ日に2回叩かれても二重通知しない）

**完了条件**
- 契約日を入れると、次回の報告期限が画面に出る
- cron を手動で2回叩いても通知は1回しか飛ばない
- 月末日・うるう年を含むテストケースが通っている
- 通知センターに履歴が並ぶ

## 10. 顧客への説明（提案時に使う言い回し）

技術的に正しいことと、伝わることは別。

### コストについて

聞かれたら答える程度でよい。先回りして長々と説明しない。

> システム自体は無料枠で動かせる設計にしています。
> ただし、実際に業務で使い始めると、LINE の配信通数とサーバー費用で
> 月数千円程度かかる可能性があります。
>
> LINE の無料枠は月200通で、これは「送った人数 × 回数」で数えます。
> 友だち50人に一斉配信すると1回で50通なので、月4回で上限です。
>
> そこで、上限に近づいたら自動で止まり、許可なく超過送信しない仕組みを入れています。
> 画面に「今月あと63件送れます」と常に表示し、配信前に確認が出ます。
> 気づいたら課金されていた、ということは起こりません。

### その他、正直に伝えるべきこと

- **既存の LINE 登録者**：認証済アカウントでない限り、こちらから友だち一覧を取得できない。
  一度メッセージに反応してもらう必要がある
- **PDF**：LINE の仕様上、PDF ファイルを直接送れない。画像かリンクになる
- **紐付け**：LINE の表示名は本名と違うことが多いため、初回の顧客紐付けだけは目視確認が必要
- **リマインドの通知先**：LINE ではなくメールにしている。
  管理物件20件で2週間ごとに通知すると月40通になり、無料枠の2割を自分宛が食うため
- **補助金の経費区分**：システム開発費は「ウェブサイト関連費」に分類されることがあり、
  上限が設けられている場合がある。商工会議所への確認を勧める
  （自分は補助金の専門家ではないと明示する）
